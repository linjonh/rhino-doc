# 配置


---
## 优化级别

当前支持的优化设置有：
|    |   |
|:---|:--|
|  -1  |  始终使用解释模式。编译时间被最小化，但牺牲了运行时性能。不生成类文件，这可能会根据系统改善内存使用。解释模式的另一个好处是解释器会执行递归函数的尾调用消除。此外，如果代码使用了 Continuation 对象，必须使用此优化级别<br/><br/>如果优化包不可用，则优化行为始终相当于 -1  |
|  0  |  不执行任何优化。字节码编译器在此模式下运行速度最快，但生成的字节码效率较低  |
|  1-9  |  执行所有优化。进行简单的数据和类型流分析以确定哪些 JavaScript 变量可以分配给 Java 虚拟机寄存器，以及哪些变量仅用作数字。局部常见子表达式被折叠（目前仅限于属性查找，但未来可能会优化更多的表达式）。所有局部变量和参数都分配给 Java 虚拟机寄存器。函数调用目标基于源代码中的名称进行推测性预缓存，从而实现直接分发，前提是运行时确认实际目标。参数作为 Object/Number 对传递，以减少转换开销  |

_注意:_

- 某些语言特性（例如对 eval 的间接调用，使用函数对象的 arguments 属性）先前在较高优化级别中不受支持。这些特性在 ECMA 中已被移除，因此较高优化级别现在符合标准。
- 未来的版本可能会为更高的优化级别分配更积极的优化。为了与未来版本的兼容性，请使用级别 1。为了获取最大化优化，请使用级别 9，但在升级到新版本时需要重新测试您的应用程序。
- 脚本是在编译时优化，而不是在执行时优化。因此，如果脚本是在 context 的 optimizationLevel 设置为 1 时编译的，那么无论它在什么 context 中执行，都会以这些优化执行。
